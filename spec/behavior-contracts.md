# Behavioral contracts and implementation readiness

These observations apply to the pinned S3 binary, not every chip or SDK version. Evidence F:name maps to supervisor-private original-body evidence. The exact exported symbols and public declarations are in the inventories. Every named family below is covered by that inventory. 'Ready' means enough functional facts for a small original implementation and focused verification, not permission to claim whole-archive equivalence. Use public SDK error constants: 0 success, 0x101 no memory, 0x102 invalid argument, 0x103 invalid state; some internal operations instead return -1.

## Interface checks and public wrappers

**Ready with public identity tokens.** `esp_coex_adapter_funcs_md5_check` and `esp_coex_i154_funcs_md5_check` accept a null argument with success. Otherwise compare the caller string with the corresponding exported expected string for the length of the expected string; a matching prefix succeeds, including a caller string with a longer suffix. A mismatch logs and returns 0x102. They are string-identity checks, not MD5 calculations at runtime. Do not substitute always-success stubs. Generate expected tokens from the pinned public header and SDK's `components/esp_coex/test_md5/test_md5.sh` process where applicable; the basic interface token is cross-library identity and needs separate resolution. Evidence F:both named check functions; public SDK test script.

`esp_coex_adapter_register` first checks the existing global adapter pointer. If already non-null, return success without validating or replacing the new argument, even if null. For first registration, null table, wrong version or wrong magic returns 0x102; otherwise retain the caller's table pointer and return success. The table is borrowed, not copied or freed here; its lifetime must cover all callbacks. Individual function pointers are not validated. Initialization serialization is a caller obligation unless strengthened explicitly. Evidence F:esp_coex_adapter_register.

`esp_coex_status_bit_set/clear`: Wi-Fi public status type 0 is rejected with 0x102. BLE type 1 accepts exactly 8, 16 or 32; classic BT type 2 accepts exactly 16 or 32; I154 type 4 accepts exactly 1. Other types are forwarded without this validation. Accepted calls invoke the matching internal status setter/clearer and return success; they cannot report the void internal operation's lock failure. This is a single-value validation, not acceptance of arbitrary OR combinations of those public constants. The header lists a smaller public enum than the implementation handles. Evidence F:esp_coex_status_bit_set/clear.

`coex_event_duration_get`, `coex_pti_set/get` forward to their core counterparts. The PTI setter narrows priority to one byte. Wi-Fi request/release adds radio selector 1, Bluetooth adds selector 0; request forwards event, latency and duration, while release forwards selector and event. Core release's unused first slot still belongs to its caller ABI. `coex_pre_init` logs version metadata then calls core pre-init. `coex_init`, `coex_deinit`, `coex_enable`, `coex_disable` forward to the corresponding core functions; honor public void return declarations for deinit/disable. Evidence F:each wrapper.

`coex_preference_set` returns success without changing state in this pinned implementation. `coex_version_get_value` rejects a null result with 0x102 and otherwise writes three bytes, version 2.0.0, then succeeds. `coex_version_get` returns a stable string; a fresh implementation must identify its build honestly while retaining the numeric compatibility API where appropriate. `coex_is_running` reports true only when core status equals 1. `coex_status_get(bitmap)` obtains the active radio-type bitmap and returns zero if no active type exists outside the caller's low-byte bitmap; otherwise returns core status. This is not simply an AND of status and bitmap. Evidence F:each named function.

`coex_wifi_register_update_lpclk_callback` replaces a private callback pointer. `coex_update_lpclk_interval` calls it only if non-null; public return type is void. `coex_register_start_cb` forwards registration to the core. Evidence F:each named function.

## Core locking, lifecycle and arbitration

**Ready lock machinery; integration prerequisites remain.** Private core lock uses the semaphore at core-state offset 0. Null handle gives 0x103. In ISR context it uses adapter take-from-ISR with a zero-initialized wake flag and yields if that output flag becomes nonzero. In task context it uses adapter semaphore take with the public infinite timeout 0xffffffff. Adapter result exactly 1 means success; any other result means -1. Private core unlock skips work for a null semaphore, otherwise uses the corresponding ISR/task give; in ISR context it yields when requested. Do not replace this with a host mutex or empty critical section. Evidence F:coex_core_lock, F:coex_core_unlock_isra_0.

`coex_core_pre_init`: if no core semaphore exists, create a binary semaphore with maximum 1 and initial 1; null creation returns 0x101. Initialize scheduler next. Scheduler failure logs, deletes the core semaphore and returns 0x101; original evidence does not show clearing the stored handle after deletion, which is a retry/lifetime edge requiring an explicit compatibility decision. On scheduler success acquire core lock; failure returns -1. Under lock call ROM OSI initialization, release lock, and propagate its result. See ROM publication contract. `coex_core_init/deinit` are success-returning no-ops in this pinned archive; do not infer cleanup from their names. Evidence F:those functions.

`coex_core_enable/disable` maintain a private **8-bit wrapping counter** under core lock. Enable increments modulo 256. If the resulting count is at least 2, write status 1, unlock, then invoke the current non-null start callback. For resulting count 0 or 1 it only unlocks. Disable decrements modulo 256 and clears status only when the new count equals 1. Lock failure yields -1 without changing count/state. These unusual thresholds and wraparound are observed compatibility facts; a normal saturating reference counter would change behavior. Callback invocation is after unlock and the callback's result does not become enable's result. Evidence F:coex_core_enable/disable; boundary recheck receipts are identified separately in the parent supervisor workspace.

`coex_core_register_start_cb` locks, stores the callback at offset 12, unlocks, succeeds. Lock failure maps to 0x103. `coex_core_status_get` reads the status word without acquiring that lock. Evidence F:these functions.

`coex_core_pti_set(event, priority)` accepts event 0–41 and low-byte priority 0–15; invalid input returns 0x102 without writing. Success writes one entry. `coex_core_pti_get` rejects null output with 0x102, otherwise reads the indexed byte and returns success; **no event bounds check is observed**. Valid-domain requirements and out-of-range handling must be documented rather than silently claiming equivalent hardening. Evidence F:both PTI functions.

`coex_core_event_duration_get` rejects null output with -1. Events 4, 7, 9, 39 and 40 read successive duration parameters and succeed. Any other event writes zero and returns -1. This algorithm is implementable independently; exact initial parameter values remain policy inputs. Evidence F:coex_core_event_duration_get.

`coex_core_timer_idx_get` maps events 1–40 through a private fixed lookup and returns 255 outside that unsigned range. Complete event-to-timer mapping is a remaining factual contract to extract; do not assume event index equals timer index. `coex_core_request` gets that index, rejects 255 with 0x102, otherwise programs the timer with radio selector, event's PTI, latency and duration, then enables it and succeeds. `coex_core_release` similarly resolves the event, rejects 255, otherwise disables that timer and succeeds. Exact policy defaults and MMIO semantics block an operational implementation of these request/release routines. Evidence F:these four functions.

## Scheduler locks, accessors and callback registration

**Ready on caller-injected valid state; policy boot remains separate.** `coex_schm_lock/unlock` use the scheduler semaphore at offset 16. Null gives 0x103. Lock uses adapter task semaphore take with infinite timeout, unlock uses task give; success requires result exactly 1, otherwise -1. Unlike core lock, these do not choose ISR variants. An ISR-safe caller contract cannot be inferred from their presence in the ROM dispatch table. Evidence F:coex_schm_lock/unlock.

`coex_schm_interval_set/get` lock around the 32-bit interval. Setter returns -1 on lock failure, otherwise writes and returns 0; getter returns 0 on failure. `coex_schm_flexible_period_set` similarly writes byte 58 under lock; getter reads that byte without locking. `coex_schm_curr_phase_idx_get` returns byte 4 under lock, or -1 on lock failure. `coex_schm_curr_period_get` returns descriptor byte 1 under lock, defaulting to 1 on lock failure or null descriptor. Evidence F:each accessor.

`coex_schm_curr_phase_get` returns a pointer to the current four-byte phase record after the descriptor's two-byte header; null descriptor, lock failure or index not below phase count gives null. The lock is released before returning the borrowed pointer, so it is not a locked snapshot. `coex_schm_get_phase_by_idx` has similar behavior with a **signed comparison** against phase count; negative inputs pass its observed upper-bound check and produce a pointer before the phase array. That is an invalid-domain compatibility hazard, not a recommended application behavior.

`coex_schm_curr_phase_idx_set` locks and requires a non-null descriptor. If Wi-Fi status is exactly 64 and requested index equals phase count, it converts the index to zero. Otherwise it uses a signed upper-bound check with no lower-bound check, then stores the low byte. After unlock it invokes the BT scheme callback with argument 0 if the update succeeded and a callback exists. It does not program the timer here. Lock/descriptor/index rejection returns -1. Evidence F:the three phase functions.

`coex_schm_register_callback` accepts only type 0 (Wi-Fi pointer at 52) and type 1 (BT pointer at 20), under scheduler lock. It accepts null callback to clear registration. Other types, including the public enum's type 2 I154, return -1; lock failure returns -1. `coex_register_wifi_channel_change_callback` stores the callback at offset 28 under lock. Its null pointer clears registration. Evidence F:both functions.

`coex_wifi_channel_set` stores low-byte primary/secondary under lock, captures the channel-change callback, unlocks and calls it with those two bytes if non-null. It calls even when values did not change; no channel-range validation is observed. `coex_wifi_channel_get` rejects either null output with 0x102; otherwise locks and copies both bytes, with -1 on lock failure. Evidence F:these two functions.

`coex_schm_status_get(type)` returns the selected Wi-Fi/BLE/BT 16-bit status under lock for types 0/1/2, zero for other types or lock failure. `coex_schm_status_bitmap_get` reads without locking and forms one active bit per nonzero Wi-Fi/BLE/BT/external/I154 status (bits 0–4 respectively). Evidence F:both functions.

## Scheduler state transitions and timer callbacks

**Partial semantic specification; not release-ready.** Internal `coex_schm_status_bit_set/clear` take type and 32-bit bits, but store only 16-bit status fields. Type mapping is Wi-Fi 0, BLE 1, BT 2, external 3, I154 4. They acquire scheduler lock and return without work if it fails. Unsupported types make no status changes. Set ORs new bits; clear ANDs the complement. Only changed-status cases select a new descriptor. Since the original changed test can inspect full input bits while stores truncate to 16 bits, high input bits need dedicated cases before claiming equivalence. Do not replace these functions with an unrestricted 32-bit bitmap API.

Set computes loop eligibility before/after modification, updates descriptor under lock, releases lock, then conditionally restarts phase processing. Clear updates descriptor under lock, releases it and does not perform the same restart sequence. The exact set restart predicate and full descriptor-selection precedence remain extraction work. Evidence F:coex_schm_status_bit_set/clear and F:coex_schm_status_change.

Loop eligibility counts active categories: nonzero Wi-Fi status; nonzero combined BLE-or-BT status; nonzero external status; nonzero I154 status. At least two categories permits looping. BLE and BT together count as one category. This is a scheduling predicate, not a device-enable count. Evidence F:coex_schm_is_loop_allowed.

`coex_schm_init` creates a binary semaphore (maximum and initial 1) if absent; null creation gives 0x101. On success it selects the all-default descriptor and installs a timeout callback for the embedded timer at offset 32, passing null callback argument. It does this timer setup even when semaphore already exists. `coex_schm_deinit` calls adapter timer_done for that object; it does not delete semaphore or reset all scheduler fields. Evidence F:both functions.

Timeout processing calls private phase change with restart=false; `coex_schm_process_restart` calls it with restart=true. Phase processing locks, disarms the timer before advancing/restarting, resets to phase zero on restart and otherwise advances according to phase/loop rules. When armed, one-shot delay is descriptor period times interval times phase duration weight, with 32-bit multiplication behavior. Wi-Fi statuses exactly 1, 2 or 64 have special terminal-phase/loop handling. The exact full terminal transition truth table is not asserted by this abbreviated spec.

The phase's first radio control byte being nonzero selects the Wi-Fi callback; either of the other two control bytes being nonzero selects the BT callback. After unlocking, it emits debug event 4/signal 2, calls selected Wi-Fi callback with argument 0, then selected BT callback with argument 0. Nonzero control bytes have more meanings to downstream consumers than this callback gating. Preserve callback capture/invocation order, timer serialization and reentrancy. Evidence F:coex_schm_change_phase, F:coex_schm_timeout_process, F:coex_schm_process_restart.

## Debug, hardware and external coexistence

**Simple callback subset ready.** `coex_set_gpio_debug_cb` registers/replaces a private callback. `coex_dbg_output` calls it with event and signal only if non-null. `coex_gpio_debug_max_event_get` returns 5. `coex_dbg_set_log_level` replaces the 32-bit exported level. `coex_gpio_debug_matrix_init/config` delegate to hardware debug routines; exact hardware effects are separate. Evidence F:these six exports.

Hardware timer exports are `coex_hw_timer_set/enable/disable/force/unforce`; hardware debug exports are `coex_hw_debug_matrix_config/init`. These operate on MMIO, not OS timers. Timer control has enable bit 31, force bit 28, selector bit 30, priority bits 24–27 and a 24-bit duration; latency is related to a hardware clock register. Full index addressing, read/modify/write ordering, clock wraparound, valid indices and register ownership require verification against public S3 register declarations and original execution evidence before fresh implementation. Debug matrix uses the registered adapter's debug-matrix callback and fixed signal mapping; enumerate that mapping before implementation. Existing zero/default fixture coverage is not a hardware proof. Evidence F:each hardware function.

`esp_coex_external_set_wire_type/get_wire_type` store/read a private 32-bit wire-type value without range validation. `esp_coex_external_set_txline` sets external status bit 2 for true and clears it for false. `esp_coex_external_set/stop` wrap `ic_set_extern_coex/ic_stop_extern_coex`. Starting calls core enable, sets external status bit 1, configures external GPIO/PTI and enables hardware; observed return is success even though core-enable status is ignored. Stopping clears external status bits 2 then 1, calls core disable, clears external PTI then disables hardware. The first start PTI argument is unused in the pinned internal body; public signatures still retain it.

External HAL exports `hal_coex_set_wait_time`, `hal_enable_extern_coex`, `hal_disable_extern_coex`, `hal_set_extern_pti`, `hal_clr_extern_pti`, `hal_set_extern_coex_gpio` need explicit register/mask contracts. `hal_set_extern_pti` consumes six argument slots, not the three-argument public external setter shape. They are not safe success stubs. Full external electrical/timing operation remains blocked pending those contracts; this spec does not authorize any hardware run. Evidence F:all named external functions.
